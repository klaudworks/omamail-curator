# Larger features

New providers, substantial integrations or workflows, and real uncertainty about the product boundary warrant discussion before implementation. Use `feature` with `fundamental` or `uncertain` scope and `needs-maintainer-decision`; the publisher tags the configured maintainers.

Ask the actual unresolved product question. State the benefit and relevant consequence of adopting the proposal, such as an added browser dependency or a supported third-party API contract. Do not repeat that feature requests require approval, say a decision is missing, or ask for a `/curator` command. The label already communicates the workflow status.

Read existing maintainer replies and relevant linked discussion first. Ordinary explicit replies count; [SCOPE.md](SCOPE.md) explains how to cite them. Honor already accepted, rejected, deferred or shipped work rather than reopening a settled decision. After acceptance, invite the creator to work with their agent on a focused PR as in [ISSUE-CHANGES.md](ISSUE-CHANGES.md). Do not promise adoption before review.

Use [EVIDENCE.md](EVIDENCE.md) to verify accessible claims and [REPORT.md](REPORT.md) to respond.
