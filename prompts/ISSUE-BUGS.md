# Bug reports

Read the report and discussion; verify accessible facts using [EVIDENCE.md](EVIDENCE.md), including source/release inclusion. A proposed cause is not an observed cause. Separate an existing-behavior defect from optional feature additions.

Use `bug` / `needs-information` only when a missing fact prevents useful investigation. Ask together for the essential reproduction, expected/actual behavior, environment or error not already supplied. Inspect relevant screenshots first. Request minimal sanitized examples, not real mail or credentials.

Supply an `author_prompt` for the creator's coding agent: the ambiguous scenario, targeted inspection/reproduction and observations to report. Let the agent collect accessible facts and ask the user only what it cannot observe. Use synthetic data and captures only when useful; never invent results or request a full suite. The publisher appends the issue URL and GitHub posting/upload instructions; do not repeat them.

Once actionable, use `bug` / `routine` / `handoff` with an author next step. Invite a focused fix PR and useful regression evidence, not a condition for reporting. Do not assign routine implementation to maintainers or require redundant media. Respect linked work: no competing PR when one already addresses the problem. For a verified shipped fix, use `verified-fixed` with its version and scope; do not demand another release check or speculative live-provider retest. Closure stays human.

Finish with [REPORT.md](REPORT.md).
