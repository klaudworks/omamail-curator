# Controller policy

Reviewer decisions are documented once, under [prompts/REVIEW.md](prompts/REVIEW.md). Repository files supply product, engineering and evidence guidelines; curator guides supply workflow, scope escalation and output rules.

## Eligibility and execution

- Process eligible open items oldest first, sequentially every 5 minutes. Configured authors and explicitly enrolled `tracked_prs` are eligible; optionally include PRs by any author created at or after `all_pr_authors_since`. The cutoff uses creation time, not updates or reopening. `all_issue_authors: true` additionally enrolls all open issues regardless of age or author, without broadening PR eligibility. Exclude draft PRs and deferred items.
- Before each PR model stage and publication, require both configured workflows and every job to succeed for the current head. Pending, missing, skipped, neutral, cancelled or failed results stop the item. Issues have no PR CI prerequisite.
- Use the configured completeness model and a fresh session for final review. Authentication, transport, tool or output failures pause work. Review-count and model-duration limits are not imposed.
- Completeness checks prerequisites without repository-wide execution; final review uses focused diagnostics. Neither stage executes or requires full repository suites. The existing current-head CI gate remains the baseline; additional evidence requests must identify a concrete unresolved scenario in changed behavior.
- Final review aims for reasonable, risk-proportionate merge confidence, not exhaustive coverage. Apply [PRS.md](prompts/PRS.md) and [EVIDENCE.md](prompts/EVIDENCE.md): batch known substantive blockers, preserve resolved findings, and do not turn reviewer environment limitations or hypothetical edge cases into automatic contributor requirements.
- Unchanged polling costs no model calls. When configured, the [relevance gate](docs/relevance.md) evaluates accumulated changes against the last full assessment using pinned Jev. Ask whether another assessment can reasonably be skipped; skip when `P(can_skip) > 0.75`, otherwise review. Incomplete evidence goes to review; API failures retry the decision later. Initial assessments always run.
- Repository content never configures the runtime. Only installed reviewer guides are instruction sources. Native OpenCode tools use a credential-free Bubblewrap workspace with no external network or model-service process access. Each stage shares disposable diagnostic copies; evidence and generated outputs are read-only. GitHub credentials and checkpoint keys remain on the controller host, outside the VM; model authentication remains in the trusted SDK host, outside tool processes. See [Isolation](deploy/ISOLATION.md).

## Publication and recovery

- Publish exactly one initial issue assessment, considering the original report and prior discussion. Use short natural paragraphs and an automated-curator attribution. After material new evidence, add an issue reply only if it provides a useful changed answer or next step; otherwise retain the assessment privately and update labels. PRs publish one new normal status comment per completed assessment. Issues also receive one category: `bug`, `enhancement` (feature), or `question` (support/disputed), plus relevant status labels. Reclassification replaces those category labels; unrelated labels are preserved. Verified maintainer rejection/deferral adds `wontfix`/`deferred` respectively; only a previously curator-applied `wontfix` is removed on reassessment. Deferred items stop until a maintainer removes that label. PR category labels are not managed. Do not also post a formal GitHub review. Never close/reopen, approve, request changes, merge, alter draft state or repair contributions.
- Actionable bug reports and small enhancements invite the creator to use their coding agent and submit a focused PR with relevant before/after evidence. Tag the author's actual GitHub login whenever assigning an author next step, on both issues and PRs. Bug clarification requires concrete missing information plus a copyable diagnostic prompt; existing evidence must be inspected first. Substantial features need a specific maintainer scope question. Ordinary maintainer replies count on issues: the reviewer interprets their meaning and the controller checks cited comment ownership and exact quotations, honors rejection/deferral and rejects unsupported scope handoff. It does not replace a useful assessment with a generic approval demand. Issues never become PR-ready. Issue and PR checkpoint contracts are versioned separately so issue-policy changes do not force PR reassessment.
- Validate output, selected-model sessions and required guide/evidence reads. Recheck creator, current head/base, CI and relevant discussion before each effect. Readiness requires a fresh final review, verified affected security boundaries and no blockers.
- When PR completeness passes, remove `needs-information` immediately after rechecking freshness and CI, before starting final review. This transition adds no comment or readiness label; final review may request information again.
- Retain verified passing PR completeness as a durable entry milestone in private controller state before final review. Later commits, base updates, title/description changes and discussion go directly to a fresh final reviewer with current evidence; recheck maintainer scope decisions and CI. Final review revisits prerequisites when scope materially changes or required evidence is removed and requests specific missing information or a maintainer decision. Completeness contract/model changes invalidate the milestone; failed checks and issues never establish one. Final publication still requires fresh code and discussion.
- Keep signed checkpoints in status comments; the newest valid checkpoint is current. Unchanged inputs reuse the assessment without another comment. Deduplicate retries by input fingerprint, contract version, phase and model-session provenance; wording corrections to that same assessment may update its comment. Policy-version changes invalidate old assessments once. Removing the current checkpoint falls back to eligible signed history or fresh processing.
- Persist completed model output before publication. Retry unfinished publication/label work with the same assessment rather than paying for another review. Private relevance baselines are anchored to the current signed public checkpoint; skipped changes never advance the fully-reviewed baseline. A skipped new PR head/base loses stale readiness and retains the original reviewed SHA.
- Discover existing comments/reviews before retrying a write. Exclude signed automated events from human decisions. Immediately recheck after publication; remove stale readiness if inputs changed. GitHub cannot make the check and mutation atomic.
- Review proposed criteria changes against the baseline guidance. Duplicate handling is deferred. Maintainers own disposition.
